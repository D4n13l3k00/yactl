# Настройка

Общий файл — `<root>/settings.json`. По умолчанию `root` равен `/data/.yactl`;
каждая команда принимает `--root PATH`. Формат — JSON с `version: 1`.
Неизвестные поля и недопустимые сочетания отклоняются. Без файла используются
настройки по умолчанию: оборудование выключено, Unix-сокеты приватные, HTTP
слушает `127.0.0.1:8098`.

## Локальные подключения

Чтобы оставить только Unix-сокет:

```json
{"version":1,"http":{"enabled":false}}
```

Менеджер использует `<root>/control.sock`, API — `<root>/api.sock` с режимом 0600.
Владелец сокета получает административный доступ; каталог должен быть приватным.
Локальный HTTP разрешает чтение без токена. Для изменений нужен bearer-токен
с соответствующим разрешением, даже через loopback. Запросы с заголовком
`Origin` не могут выполнять изменения.

## Адаптеры

| Настройка | Реализации |
| --- | --- |
| `lighting.backend` | `off`, `simulate`, `framebuffer` |
| `clock.backend` | `off`, `simulate`, `sysfs` |
| `sensors.backend` | `off`, `simulate`, `sysfs` |
| `volume.backend` | `off`, `simulate`, `alsa` |
| `input.backend` | `off`, `simulate`, `evdev` |

По умолчанию везде `off`. Аппаратная реализация требует подтверждённых
интерфейсов; `device.model` не обходит обнаружение оборудования. Для `evdev`
нужен явный список `input.devices`. Подписки прошивки включаются отдельно через
loopback-адреса или поиск выбранных сервисов. Подробности — в [справочнике API](../api/index.md).

[Пример для Миди](../../deploy/settings-midi.example.json) включает аппаратные
адаптеры, выбранные кнопки и поиск aliced. Симуляция нужна для разработки и
не подтверждает работоспособность физического устройства.

## Доступ по HTTP

В `keys` каждая запись задаёт абсолютный путь к файлу токена и список `scopes`:
`read`, `hardware`, `services`. Файл должен быть обычным, приватным и принадлежать
пользователю API-процесса. Не помещайте значения токенов в настройки или репозиторий.
Передавайте токен заголовком `Authorization: Bearer TOKEN`.

- `read`: идентификация, состояние, возможности, датчики, ввод, события и состояние ресурсов.
- `hardware`: потоки подсветки и часов, изменение громкости.
- `services`: управление сервисами и применение настроек.

Для адресов вне loopback обязательны настроенные учётные данные.
`http.access: "lan"` также требует явных CIDR в `http.allow`: привязка к wildcard
сама по себе не ограничивает доступ локальной сетью. Режим `all` снимает это
ограничение адресов и включается только явно. Диапазоны IPv4 и IPv6 раздельны.
Заголовки пересылки клиентского адреса не считаются доверенными. Встроенного TLS
нет; для удалённого доступа нужен доверенный TLS-прокси или эквивалентная защита.

## Проверка и применение

```sh
yactl check
yactl daemon-reload
```

`check` проверяет настройки и токены без изменения состояния. Reload сначала
проверяет полный новый вариант. Ошибки настроек, ключей или нового слушателя
оставляют активную конфигурацию без изменений. Смена аппаратной реализации,
списка ввода или адресов прошивки требует перезапуска API-процесса: reload сообщает
об этом вместо частичного применения.

`device.display_name` и `device.model` (`midi` или `unknown`) можно менять через
reload. Постоянный идентификатор экземпляра не зависит от имени, IP или названия
устройства. Результаты обнаружения сохраняются и при ручном указании модели.

Запись сервиса перечитывается отдельно: `yactl services reload NAME`.

## Основные маршруты

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/v1/health` | Готовность API, менеджера и адаптеров |
| GET | `/v1/device` | Постоянная идентификация и сведения обнаружения |
| GET | `/v1/capabilities` | Проверенные операции и геометрия |
| POST | `/v1/config/reload` | Транзакционное применение настроек |
| POST | `/v1/services/request` | Существующий JSON/RPC-контракт сервисов |

В CLI доступны `health`, `device`, `capabilities` и `--json` для скриптов.
`health.ready` относится к API; `health.supervisor.ready` требует живого ответа
менеджера. Поддержка адаптера и его текущая готовность различаются. Настроенный
источник не считается автоматически проверенным.

Пересылка сервисных запросов допускает четыре одновременных блокирующих вызова;
при перегрузке возвращается HTTP 503. Ключ для оборудования не даёт права
запускать произвольные процессы или администрировать сервисы.
