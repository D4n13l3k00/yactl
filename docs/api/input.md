# Кнопки и переключатели

Адаптер только читает ввод и выключен по умолчанию:

```json
{"input":{"backend":"evdev","devices":["vad_keypad","mute","awinic_sar"]}}
```

`input.backend` принимает `off`, `simulate`, `evdev`. Смена реализации или списка
требует перезапуска API; reload сохраняет активную конфигурацию. Для физического
ввода нужны настоящие сведения Cucumber из device-tree, а не ручная модель.
На другом Linux можно использовать симуляцию.

## Выбор и состояние

Для evdev нужен непустой список: до 16 уникальных имён по 1..63 байта UTF-8,
без управляющих символов. Совпадение точное, имена не интерпретируются как пути.
Симуляция использует собственное устройство и отклоняет список выбора.
Отсутствующие имена возвращаются в `missing_devices`, без подмены другим источником.

`GET /v1/input` требует `read` и возвращает кэш описаний и состояний.
`input.events.v1` объявляется после проверки интерфейса и начального снимка.
Поддержка и текущая готовность раздельны. Выключенный адаптер возвращает пустой
список и не объявляет возможность. Записи и внедрения ввода нет.

`age_ms` отсчитывается с последнего завершённого опроса. Через 3000 мс без
прогресса `ready` становится false, `state` — null, ошибка — `input_stale`.
Успешные тихие чтения обновляют свежесть без выдуманных нажатий. Историческая
поддержка при этом сохраняется.

## Обнаружение и выполнение

Сканируются только event0..event31, открывается не более 16 выбранных устройств.
Сначала читается ограниченное sysfs-имя, затем для совпавшего узла проверяются
тип символьного устройства, major ввода, имя через ioctl, биты возможностей и
начальный снимок. На Миди наблюдались `input_btrcu`, `vad_keypad`, `mute`,
`awinic_sar`; другое выбранное имя проходит те же проверки. Невыбранные узлы
не открываются. Допустимы до 64 кодов клавиш и 32 кодов переключателей на устройство.
Дескрипторы read-only с `O_NOFOLLOW` и `O_NONBLOCK`; захватов и записывающих ioctl нет.

Один отдельный поток вне Tokio и менеджера читает до 32 записей с устройства
каждые 20 мс. Обработчик API лишь копирует ограниченный кэш. Остановка будит
поток и ждёт до 500 мс; блокирующий вызов ядра не считается отменяемым.
Неисправимая ошибка чтения отключает только этот источник и публикует потерю.
Для повторного обнаружения нужен перезапуск. Hotplug/reopen не реализованы.

## События

В общем [журнале](events.md) публикуются:

| Тип | Данные |
| --- | --- |
| `key` | `type: 1`, числовые `code`, `value`: 0 — отпускание, 1 — нажатие, 2 — повтор |
| `switch` | `type: 5`, `code`, `value`: 0 или 1 |
| `input_snapshot` | `reason: initial` или `resync`, массивы `keys_down`, `switches_on` |
| `source_loss` | `reason: syn_dropped` или `input_read_failed`; `count: null` |

Источник `input:device-N` обозначает позицию в списке выбора, не Linux event-индекс.
Имена узнаются через `/v1/input`. Перестановка списка требует перезапуска и меняет
поколение истории. Симуляция использует `input:simulated`.

Коды остаются кодами Linux: имя `mute` само по себе не доказывает состояние
микрофона. Неизвестные типы игнорируются; необъявленный код или неверное значение
считаются ошибкой источника. События не меняют громкость и другое оборудование автоматически.

После `SYN_DROPPED` источник временно неготов, состояние скрывается, записи до
следующего `SYN_REPORT` отбрасываются. Затем `EVIOCGKEY`/`EVIOCGSW` дают новый
снимок и готовность возвращается. Это соответствует
[контракту Linux input](https://docs.kernel.org/input/event-codes.html).
Снимки разных ioctl не глобально атомарны. При переполнении журнала клиент
запрашивает `/v1/input` для восстановления состояния: все переходы не гарантированы.

## Проверки

Linux LP64 `input_event` занимает 24 байта, смещения type/code/value — 16/18/20.
Декодирование не требует выравнивания или приведения указателей. Rust-утверждения
и независимая проверка C-заголовков закрепляют размеры и read-only ioctl.
Тесты покрывают потерю/синхронизацию, неверный ввод, остановку во время проб,
неизвестный хост, авторизацию, переполнение и устаревание. Симуляция меняет key 115
и switch 14 раз в 100 мс. На Миди проверены четыре устройства, снимки, открытие
только выбранных дескрипторов и физическое нажатие/отпускание `awinic_sar`.
См. [испытания](../development/verification.md).
