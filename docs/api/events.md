# События

`GET /v1/events` доступен через приватный сокет и HTTP с разрешением `read`.
Явно включённые [источники прошивки](firmware.md) и [ввода](input.md)
публикуют события в общий журнал. Без источников он пуст, возможности событий
не объявляются. Публичного маршрута для внедрения событий нет.

## Как читать новые события

API возвращает `cursor` — номер последнего события в полученной странице.
Передайте его как `after` в следующем запросе, чтобы продолжить чтение.
Например, после ответа с `cursor: 42` запрос с `after=42` вернёт события после 42.

Вместе с номером сохраняйте `stream_id`: это идентификатор текущей истории.
Он меняется при перезапуске API. Так клиент отличает продолжение чтения от
нового журнала. Сам журнал хранит только последние 64 события; `lost` сообщает,
сколько записей клиент пропустил.

### Параметры запроса

Первый запрос не требует query. Ответ содержит `stream_id`, `events`, `cursor`,
`latest`, `lost`, `closed`. Последующие запросы передают одновременно `stream_id`
и `after`:

```text
GET /v1/events?stream_id=0123456789abcdef0123456789abcdef&after=0&limit=16&wait_ms=2000
```

`limit` по умолчанию 16, допустимо 1..16. `wait_ms` по умолчанию 0, максимум
2000 мс. Числа — десятичные без знаков и кодирования; ID — 32 строчных hex-символа.
Повторы, неизвестные параметры, percent-encoding, переполнение и неполная пара
курсора дают HTTP 400 `invalid_request`. Query ограничен 256 байтами.

Курсор из будущего даёт HTTP 409 `invalid_event_cursor`. Смена истории — HTTP 409
`event_stream_reset` с текущим `stream_id`: клиент должен явно начать новое чтение
и синхронизировать своё состояние. Ошибки не продвигают курсор и не удаляют записи.
Ответы журнала и ошибки query/курсора содержат `Cache-Control: no-store`.

`after` исключает указанную запись. `cursor` — номер последней возвращённой,
`latest` — последней опубликованной, `lost` — число недоступных записей после
исходного курсора. Продолжайте от `cursor`, иначе можно пропустить страницы.
Для слишком старого курсора возвращаются доступные записи с явным числом потерь.

## Хранение и ограничения

`events::Journal` хранит 64 последние записи, максимум 1024 байта JSON на запись,
включая метаданные и экранирование. Недопустимая запись не расходует номер и не
вытесняет историю. Идентификаторы источника и типа — 1..64 ASCII-символа: буквы,
цифры, подчёркивание, дефис, точка, двоеточие. Производитель также ограничивает
разбор и выделение памяти до создания записи.

Номера начинаются с единицы, возрастают для всех источников и не переполняются.
Время — миллисекунды настенных часов, без гарантии порядка. Журнал живёт в памяти
API-процесса. Случайный 128-битный `stream_id` меняется при перезапуске, сохраняется
при reload и не связан с постоянной идентичностью колонки.

Отдельных клиентских очередей и постоянных курсоров нет. Отмена чтения не
потребляет записи. Публикация будит всех ожидающих; регистрация уведомления и
проверка состояния исключают потерю пробуждения. Общий транспорт допускает
32 соединения, его сроки запросов применяются и здесь. Синхронные блокировки
защищают только ограниченные операции в памяти и не удерживаются через await или I/O.
Закрытие запрещает новые записи, будит читателей и оставляет историю доступной.

## Проверки и потребители

Синтетические проверки покрывают данные, страницы, переполнение, авторизацию,
строгий query, конкурентное ожидание, reload и смену истории. Сырые логи и речь
устройства в тесты не включаются.

Миграция приложения должна покрывать все зависимости: индикатору CPU с голосовым
триггером недостаточно заменить только запись часов. Такие программы остаются
внешними клиентами API. Нативные final-command,
будильники и перенос потребителей остаются открытыми пунктами
[плана](../development/roadmap.md).
