# RGB-подсветка

`POST /v1/lighting/stream` принимает поток `application/x-ndjson` с разрешением
`hardware`. Сессия захватывает кольцо и логотип вместе; конкурент получает
`ownership_conflict`. Адаптер выключен по умолчанию. `lighting.backend` принимает
`off`, `simulate`, `framebuffer`. Смена реализации требует перезапуска API;
`daemon-reload` отклоняет её без изменения активных настроек. Ручное указание
модели не включает оборудование.

## Формат кадров

Каждая строка — полный RGB-кадр:

```json
{"sequence":1,"ring":[[255,0,0]],"logo":[[0,0,0]]}
```

Пример сокращён: для Миди нужны ровно 24 пикселя кольца и 6 пикселей логотипа,
по три целых байта на пиксель. Запись ограничена 4096 байтами. `sequence` строго
возрастает внутри сессии. Принятый кадр поставлен в очередь, но ещё не обязательно
записан. Очередь хранит только последний кадр; ожидающие кадры старше 250 мс
отбрасываются. Запись выполняет отдельный поток. Начатый системный вызов нельзя отменить.

## Владение и восстановление

Неактивная сессия истекает через 1000 мс. Корректные кадры продлевают срок.
EOF, разрыв соединения, тайм-аут или ошибка формата освобождают ресурс.
Освобождение и истечение срока отменяют ожидающие кадры до восстановления
снимка, сделанного при захвате. Новый владелец ждёт завершения восстановления.
Штатная прошивка работает вне этого механизма.

Восстановление выполняется по возможности при штатном освобождении или остановке.
SIGKILL, потеря питания и зависший вызов ядра не дают такой гарантии. Перезапущенный
процесс не располагает снимком предыдущего. Сбой клиента не должен останавливать
менеджер сервисов. Эффекты и OpenRGB остаются в отдельном приложении.

## Состояние и ошибки

`GET /v1/lighting/status` сообщает `owned`, `owner_id`, готовность, ошибки и
кэшированный кадр. При захвате кэш обновляется из свежего аппаратного снимка
до подтверждения владения; затем — после принятых записей. Это не постоянное
наблюдение за чужими изменениями.

Поддержка физического RGB появляется в `/v1/capabilities` только после проверки
имён framebuffer и геометрии. Неожиданные параметры делают адаптер неготовым.
Симуляция помечается отдельно. Сборка проекта сама по себе ничего не включает
в конфигурации колонки.

| Код | HTTP | Причина |
| --- | --- | --- |
| `invalid_frame` | 400 | Неверный кадр |
| `ownership_conflict` | 409 | Ресурс занят |
| `stale_frame` | 409 | Невозрастающий номер |
| `lease_expired` | 408 | Истёк срок активности |
| `unsupported_hardware` | 501 | Адаптер выключен или не поддерживается |
| `provider_unavailable` | 503 | Проверенный адаптер сейчас недоступен |

Ошибка HTTP завершает сессию. Только авторизованный поток освобождён от общего
срока HTTP-запроса; у каждого полного кадра собственный срок ожидания. Частичные
чанки его не продлевают. Разрешение проверяется при открытии потока.

Клиент подсветки подключается через `--yactl-socket PATH` и передаёт RGB с уже применённой
яркостью. yactl лишь преобразует порядок каналов в BGR драйвера. Общих исходников
и зависимости сборок между репозиториями нет.

## Проверки на Миди

Проверены запись, независимое чтение результата и точное восстановление после
освобождения. Отдельный клиент использовал API без framebuffer-дескрипторов;
штатное освобождение и SIGKILL клиента восстанавливали состояние оборудования.
Подробности — в [проверках на устройстве](../development/verification.md).
