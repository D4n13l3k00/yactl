# API станции

Для локального приложения используйте `/data/.yactl/api.sock`. Сокет приватный,
его владелец имеет административный доступ. HTTP по умолчанию слушает
`127.0.0.1:8098`: чтение разрешено локально, изменения требуют bearer-токен.
Для удалённого доступа нужны явная политика и защита транспорта.
[Настройка доступа](../guide/configuration.md) описывает scopes и ограничения.

## Первый запрос

С запущенным yactl:

```sh
curl --unix-socket /data/.yactl/api.sock http://localhost/v1/health
curl --unix-socket /data/.yactl/api.sock http://localhost/v1/capabilities
```

Сначала проверьте состояние и возможности. Не выбирайте аппаратный путь по
названию модели: поддержка и текущая готовность различаются. Пустой список
возможностей при выключенных адаптерах — нормальный результат.

| Задача | Маршруты | Документ |
| --- | --- | --- |
| Идентификация и готовность | `/v1/device`, `/v1/health`, `/v1/capabilities` | [Устройство](device.md) |
| Кадры RGB | `/v1/lighting/status`, `/v1/lighting/stream` | [Подсветка](lighting.md) |
| Время и сегменты | `/v1/clock/status`, `/v1/clock/stream` | [Часы](clock.md) |

## Общие правила

Все маршруты версионированы через `/v1`. Обычные ответы — JSON; потоки RGB и часов
принимают NDJSON. Размеры запросов, число соединений и сроки ожидания ограничены.
Не считайте HTTP-тайм-аут отменой начатого блокирующего аппаратного вызова.

`read` даёт чтение, `hardware` — аппаратные изменения, `services` — управление
сервисами и reload. Аппаратный ключ не даёт права запускать произвольные процессы.
Точные ошибки и ограничения приведены в документации каждого ресурса.

Потоки требуют регулярных полных кадров. Владение, номер кадра и срок активности
относятся к одной сессии. Для событий сохраняйте пару `stream_id`/`cursor` и
обрабатывайте потерю истории, а не только очередную запись.
